# DSH Desktop 本地开发、更新与验收

适用于本仓库的「跨平台账号看板」。目标是让本机 DSH Desktop 实际运行本轮修改，不涉及发布、市场投稿或 Git 推送。

依据：[官方工作台开发规范](https://dshdesktop.com/workbench/docs/development.md)（读取日期 2026-10-17，文档版本 2026-10-09）。每次开发前重新核对官网；下列路径与命令是本机已探测到的能力，不应直接推广到其他机器或版本。

## 1. 先明确交付边界

**修改源码、构建成功、浏览器预览通过，都不会自动更新已安装的 Desktop 工作台。** Desktop 加载的是其插件安装目录里的包，不是当前 Git 工作目录，也不会替作者构建客户端。

完整更新路径：

`确认需求 → 功能分支开发 → 测试与构建 → 打包并检查包内容 → 安装该包 → 必要时重启 → 宿主内验收`

本地安装与 Git 操作相互独立。**未经用户明确授权，不提交、不合并、不推送**；「继续开发」「做完」「更新本机」不自动授权这些操作。开发前新建本地功能分支，保留原有未提交修改；用户 review 后另行决定如何处理分支。

最终报告必须区分这些状态：

| 状态 | 所需证据 | 不能据此宣称 |
| --- | --- | --- |
| 实现与测试完成 | 本轮代码、测试结果 | 已更新 Desktop |
| 构建与打包完成 | 实际 tgz、包内容和 SHA-256 | 已安装 |
| 安装完成 | 安装命令成功、安装文件核对 | 当前进程已加载新代码 |
| 配置确认 | 当前 profile 中有本包插件层 | 注册与界面正常 |
| 宿主加载确认 | 重启后的已安装条目、切换入口、真实业务界面 | 所有业务验收通过 |
| 本机自测通过 | 官方第 8 节全部适用项有本轮证据 | 已发布或已获用户 review 通过 |

## 2. 开发前检查

1. 优先复用当前对话中已确认的业务目标、目标用户、功能范围和核心流程。通用开发指令、目录名、示例代码本身不是业务需求；不明确时每次只问一个必要问题，先停在需求确认阶段。
2. 检查 `git status --short`、包管理器、脚本、目标平台和架构；记录并保留他人的修改。不要为开始工作重复询问已知名称、作者或项目信息。
3. 在目标 Desktop「关于」中记录实际版本。安装包元数据可用于辅助探测，但不能冒充已查看「关于」。2026-10-17 本机应用元数据为 **0.12.0 / macOS arm64**；历史 0.11.1 验收不代表当前版本。
4. 明确布局。本看板沿用 `customFrame: true` 的业务整页模式；首次无会话即可使用，不自动创建会话。响应式布局按业务容器宽度判断，保留宿主侧栏、市场和模式切换入口。

## 3. 包与构建的对应关系

| 文件或入口 | 作用 |
| --- | --- |
| `src/client.js` | 共享业务界面源码 |
| `lib/client.js` | DSH 加载的已构建单文件模块 |
| `dsh/index.js` | 服务端入口与 Schemastery Config |
| `cordis.patch.yml` | 用 npm 包名插入本工作台插件层 |
| `package.json` | npm 名称、版本、导出、DSH 声明和打包范围 |
| `lib/standalone.js` | 独立运行界面，不作为 DSH 预编译客户端分发 |
| `.preview/` | 浏览器测试夹具，不能代替原生宿主验收 |

必须保持：`dsh.bundle.patch` 指向 patch；`dsh.client.platform` 为 `web`；`dsh.client.inject` 包含 `dsh-desktop-workbenches`；服务端和客户端导出存在；客户端模块 id 与 npm 包名一致；注册通过 `ctx.effect` 管理生命周期。

不要随意改 npm 包名、patch 条目 id、注册 repository 或数据根目录来「刷新」安装。这些字段涉及插件身份、会话归属与已有数据。配置 patch 会整体替换同一条目的 config，不能假设它会合并。升级不能清空账号、授权、会话或宿主设置。

## 4. 测试、构建、打包

在项目根目录执行，前一步失败就停止并修复：

```sh
# 首次准备环境或依赖变更时执行；已有正确依赖无需每次重装。
pnpm install --frozen-lockfile

pnpm test
pnpm build
pnpm check

mkdir -p .install
pnpm pack --pack-destination .install
```

`pnpm build` 同时构建 DSH 客户端与独立版客户端；`pnpm check` 调用 `scripts/check-workbench-package.mjs`。`pnpm start` 启动独立版，不能用来更新 Desktop。

交付独立版浏览器访问链接时，必须说明[首次授权与换浏览器](USAGE.md#首次授权与换浏览器)：授权码只能成功使用一次，登录状态不跨浏览器共享。请用户直接复制完整链接到目标浏览器，不能先在聊天内打开再转交。Agent 不得先打开待交付链接做验收而消耗用户的授权码；授权测试应使用隔离实例。交付前确认用户服务仍在监听，并说明如何保持服务运行；不要把“服务退出”和“授权失败”混为一谈。真实授权链接、Cookie 和登录文件不得写入文档或版本库。

使用 **本次 pack 实际输出的文件**，不要安装旧 Release 或只凭文件名选包。更新版本时同步相关元数据并重建；同版本本地迭代必须用包哈希与安装文件哈希区分，不能仅凭「都显示 0.6.2」认定是新代码。不要为本地更新自动创建 Git tag 或公开 Release。

```sh
PSW_VERSION="$(node -p 'require("./package.json").version')"
PSW_TARBALL="$PWD/.install/dsh-workbench-personal-social-local-${PSW_VERSION}.tgz"
tar -tzf "$PSW_TARBALL"
tar -xOf "$PSW_TARBALL" package/package.json
shasum -a 256 "$PSW_TARBALL"
```

核对归档内的 `package.json`、`cordis.patch.yml`、`dsh/index.js`、`lib/client.js` 及其运行依赖；确认打包的是最新构建，检查大小与敏感文件。包中不得包含真实账号、连接码、飞书密钥、浏览器资料、会话、日志或备份。`files` 白名单应包含包内说明引用的必要文件。

如果安装或构建需要额外生命周期脚本，先确认脚本内容与必要性，按已有授权执行；不为解决失败而盲目放开全部脚本。

## 5. 探测并安装到目标 Desktop

先检查 Desktop 当前提供的本地安装入口，或运行随附 CLI 的帮助，确认支持本地 tgz。不要猜测不同版本有相同按钮、路径或参数。

以下为本机 macOS 已探测命令。它使用 Desktop 自带 Node/pnpm 和 Desktop 的 `web` profile；不要误装到独立 Harness、其他 profile 或全局 npm。

```sh
PSW_DSH_HOME="$HOME/Library/Application Support/dsh-desktop/harness"
PSW_DSH_CLI='/Applications/DSH Desktop.app/Contents/Resources/app.asar/node_modules/@deepseek-ai/dsh/lib/bin.js'

PATH="$PSW_DSH_HOME/.desktop-bin:$PATH" \
DSH_HOME="$PSW_DSH_HOME" \
"$PSW_DSH_HOME/.desktop-bin/node" "$PSW_DSH_CLI" \
plugin --profile web add --help
```

只有帮助明确列出 tarball 输入后，才使用上一节的 **PSW_TARBALL** 安装：

```sh
PATH="$PSW_DSH_HOME/.desktop-bin:$PATH" \
DSH_HOME="$PSW_DSH_HOME" \
"$PSW_DSH_HOME/.desktop-bin/node" "$PSW_DSH_CLI" \
plugin --profile web add "$PSW_TARBALL" \
--offline --ignore-scripts --config.auto-install-peers=false
```

这些参数是本机做法，不是所有版本的固定契约。`--offline` 需要依赖已缓存；失败时先定位缺失依赖，不能声称安装成功。保留输出并核对安装后的包版本、客户端与服务端内容。不要直接覆盖安装目录冒充包安装，也不要手改宿主私有记录或删除同名条目来绕过加载异常。

安装目录的客户端应与本轮构建逐字节相同，例如本机路径下：

```sh
cmp lib/client.js "$PSW_DSH_HOME/profiles/web/node_modules/dsh-workbench-personal-social-local/lib/client.js"
cmp dsh/index.js "$PSW_DSH_HOME/profiles/web/node_modules/dsh-workbench-personal-social-local/dsh/index.js"
```

`cmp` 只证明安装文件已更新。必要时按当前 CLI 支持的 `--profile web --dump-config` 检查本包插件层；不要把完整配置或令牌写入版本库、截图或报告。配置存在仍不能替代原生界面证据。

## 6. 重启与打开

安装后遵循当前宿主的加载/重启提示。

- **Agent 正在目标 DSH Desktop 会话内运行**：不得自行关闭或重启 Desktop/Harness，不得用 `ps`、`pgrep` 等进程探测管理重启。请用户完整退出并重新打开；重启后的项目暂记待验证。
- **Agent 运行在目标应用之外**：可按正常应用重启流程操作，确认没有未保存工作或正在执行的任务，不通过强杀进程完成更新。
- 无法操作原生 UI 时，准确说明能力缺失，交付包与安装证据；不得用浏览器预览截图冒充宿主加载。

向用户提供两条可选路径：

1. **直接试用**：重开 Desktop，展开左侧栏，点击左上角「工作台」右侧的当前名称／切换区域，选择「跨平台账号看板」。若未显示，到工作台市场的「已安装」检查条目和运行状态，加载或启用成功后再切换。新本地工作台加载后自动进入菜单，**没有单独的「添加」按钮**。
2. **继续 Agent 验收**：用户回来告知「重启好了」，再按下节检查。用户也可自行试用，不必回到开发对话；未被 Agent 实测的项目继续注明待验证。

## 7. 宿主内验收与记录

每轮建立 `docs/validation/YYYY-MM-DD-主题.md`，分别记录「通过 / 失败 / 待验证 / 不适用及原因」。旧版本结果只能引用为历史记录，不能勾作本轮通过。

- **包与配置**：Desktop 版本、操作系统、架构、包版本、tgz 路径、SHA-256、安装入口、命令退出状态、本包插件层。
- **已安装的工作台**：本轮真实列表条目、版本、运行状态；重复条目或加载失败单独记录。
- **左侧入口**：从切换器进入看板、切回原生会话，核对菜单、图标、焦点和侧栏状态。
- **真实业务界面**：保留 DSH 原生截图或可复查 UI 证据。确认本轮新增内容确实出现；浏览器预览和独立版证据单独标明。
- **布局**：首次无会话、已有工作台会话、侧栏展开/收起、窄窗口；长中文、英文标识、数字与按钮不裁切、不单字竖排、不整页横向溢出；弹层不覆盖宿主公共入口。
- **本轮四项交互**：连接文案；滚动到底部仍可见的成功/失败提示；返回总览与回顶；帮助/设置反馈入口与诊断预览复制。用合成数据验证，不为验收随意触发真实平台采集或上传真实账号信息。
- **会话/工作区（适用时）**：目录选择取消无副作用、创建/恢复归属正确、草稿由用户发送、业务选择恢复；无关能力记不适用并说明原因。
- **宿主责任**：模式筛选、工作台会话图标、跨工作区归属与卸载后数据保留按官方第 8 节核验。不要为勾选测试清理用户数据或改写归属；未做的操作记待验证，宿主缺陷单独记录。

最终先说：现在能做什么、如何打开、哪些操作实测、哪些还待验证。再简要列修改文件与技术检查。不能以「安装命令成功」或「测试全绿」总结为「全部完成验收」。

## 8. 常见的未更新原因

| 现象 | 先检查 |
| --- | --- |
| 预览是新界面，Desktop 还是旧界面 | 有没有从本轮构建 pack 并安装；安装目录客户端是否相同 |
| 安装版本号没变化 | 是否同版本本地迭代；用 SHA-256 和内容判断，不能只看版本 |
| 磁盘文件已更新，当前界面仍旧 | 宿主是否仍运行旧模块，是否完成所需重启 |
| 配置有插件，但切换器没有 | 已安装列表运行状态、服务端加载错误、客户端注册与身份是否一致 |
| 两个同名条目 | 核对安装来源和历史身份；保留用户会话，不私自清理迁移 |
| 只在 Desktop 的窄业务区排版异常 | 按真实容器宽度复验，不以整窗或独立浏览器尺寸替代 |
